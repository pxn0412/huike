# 两个智能体 · 设计文档（v0.2 讨论稿）

> 2026-09-20。约束来源：`00-整体产品逻辑.md`、`02-学生竞赛画像.md`、`03-智能组队匹配.md`、
> `2026-09-20-画像v1-字段与确认规则.md`。本稿只讨论"怎么设计与实现"，不含已冻结的边界改动。

## 一、目标与范围

**本版要做**
- 两个入口，各由一个**主智能体**负责：比赛资料问答（入口 A）、学生画像（入口 B）。
- 入口决定主智能体：进哪个入口，那个入口的智能体就是主。
- 画像能**保存、编辑**；画像智能体能**读懂已保存的画像**并在其上修改。
- 交叉问题按**先 A 后 B**处理（官方要求在前，个人情况在后，结论留给人）。

**本版不做**（红线，越界即返工）
1. 团队缺口诊断；2. 队友推荐/排序/能力评分；3. AI 生成招募需求或招募帖；4. 资格结论。

## 二、总体形态：两个入口 + 一个多智能体应用

```text
我们的网站
├─ 入口 A：比赛空间 → 问答        → 请求带 entry=competition
└─ 入口 B：我的画像 → 生成/编辑    → 请求带 entry=profile

腾讯云（一个多智能体应用）
├─ 主调度（只做转交）
├─ 子智能体 A：比赛资料问答
└─ 子智能体 B：学生画像
```

### 入口与主智能体的绑定方式

我们无法给每个入口单独分配平台路由，所以**由我们的服务端在提示词前置一行入口声明**：

```text
【当前入口：学生画像】本次以「学生画像」为主智能体；只有涉及比赛规则/资格/时间/材料时，才转交「比赛资料问答」。
【当前入口：比赛资料问答】本次以「比赛资料问答」为主智能体；涉及个人自述整理时，转交「学生画像」。
【当前入口：自动】未指定入口（评委直接扫码）：先判断用户要问规则还是整画像，再决定主智能体。
```

- `entry=competition` → 主 = A；`entry=profile` → 主 = B；扫码/未知 → 自动判断。
- **已知不确定项**：平台的多智能体"自由转交"是否严格听从入口声明，需要用 4 个用例实测（见第八节）。
  若实测发现它不听话，退路是：**网站侧不再依赖平台路由**，`entry=competition` 直接问 A、`entry=profile` 直接问 B（等于回到两个应用的确定性调用），多智能体只留给扫码入口演示。

## 三、Agent A：比赛资料问答

**定位一句话**：比赛的官方说明书查阅员 —— 有依据就答并标来源，没写就直说，不猜。

| 项 | 规定 |
| --- | --- |
| 唯一依据 | 知识库里的比赛资料（按比赛标签隔离检索） |
| 输入 | 用户问题 + `【当前比赛：X（届次）】`（网页端注入） |
| 输出 | ① 结论 ② 依据（文件名/引用角标）③ 资料支持到哪里 |
| 人格 | 严谨、克制；不寒暄过多，先给结论再给依据 |

**输出契约**

```text
【结论】…（直接回答）
【依据】[角标] 文件名 · 平台参考来源；平台未给角标时写"本条未标注可核对引用"
【说明】资料只支持到哪里；未写的内容明确说"资料中未找到"
```

**硬边界（6 条）**
1. 不用常识补全；联网搜索保持关闭；
2. 不混合不同比赛/届次/赛道；未指明比赛先确认；
3. "未找到限制" ≠ "没有限制"；
4. 日期/时间/人数/金额**逐字引用**，不换算、不近似；
5. 资料冲突时并列（来源 + 时间 + 适用范围），**不擅自判定哪份有效**；
6. **不下个人资格结论**：只给官方要求原文，再按需转 B 说明自述情况。

**失败与转交**
- 检索不到 → "当前资料中未找到相关说明"（不猜、不补）。
- 平台报错/空响应 → 网页显示失败并提供重试（绝不假装回答）。
- 涉及个人情况 → 转 B（保留比赛范围限定）。

**验收用例**
| # | 输入 | 期望 |
| --- | --- | --- |
| A1 | 慧科杯：一个人能参加吗 | 引原文回答，带角标 |
| A2 | 移动杯：报名时间 | 只用移动杯资料（不串慧科杯/计设） |
| A3 | 问了资料没写的事 | 直说"资料中未找到" |
| A4 | 两份资料冲突（若有） | 并列来源与时间，不判定 |
| A5 | 日期问题 | 逐字引用"6 月 20 日 18:00" |
| A6 | "我能拿奖吗" | 只给评选标准原文，不下结论 |


## 四、Agent B：学生画像

**定位一句话**：自我介绍的整理员 —— 只整理你说过的，不替你吹，也不替你做决定。

| 项 | 规定 |
| --- | --- |
| 唯一依据 | 学生自述 + **已保存的画像**（作为基线注入） |
| 输入 | ① 自由文本 ② 表单字段 ③ 已有画像 + 修改指令 |
| 输出 | 固定结构草稿 + 信息缺口；**联系方式不进草稿**（单独区） |
| 人格 | 平和、具体、鼓励但不夸大；像帮你改自我介绍的学长 |

**输出契约（固定结构）**

```text
【一句话介绍】专业 + 年级 + 最想突出的方向
【技能】名称 —— 正在学习／了解／能独立完成（本人自述）
【项目经历】项目名｜本人负责什么｜用到的工具｜作品链接（可选，标"本人提供"）
【比赛经历】比赛名｜本人贡献
【希望尝试】方向或角色
【每周可投入时间】可选
【信息缺口】还缺哪 1-3 条信息（只列缺什么，不推断缺什么人）
```

**硬边界（7 条）**
1. 不根据专业/年级推断技能；
2. 不把"正在学"改成"已经会"（掌握状态只按原话就近落档，三档：正在学习/了解/能独立完成）；
3. 不把团队成果全归本人，只写"本人负责的部分"；
4. 含糊时只追问一句："这件事里你本人负责什么？"；
5. 只出草稿，**没有用户确认不许说"已保存"**；
6. 改内容后原确认失效，必须**重新确认**；对外展示是**独立开关**；
7. 不判断资格、不打分、不排名、不代写招募需求；资格类问题**转交 A**。

**编辑模式（读懂已有画像）**

注入格式（我们服务端拼）：

```text
【已保存画像｜版本 v3｜确认时间 2026-09-20 15:02｜内容哈希 a1b2c3d4】
{…画像 JSON…}
```

模型在这条路径上必须遵守：
1. **只改用户指明的地方**，其余字段原样保留（含"本人自述"标记与掌握状态）；
2. 不得新增画像里没有的事实（包括"顺手润色"成更厉害的表述）；
3. 输出时列出**变更清单**（改了哪个字段、从什么改成什么）；
4. 若用户要求删掉某条 → 删除并在变更清单里写明；
5. 基线哈希与当前草稿不一致时，提示"画像已被修改，请确认以哪一版为准"。

**失败与转交**
- 信息不足 → 列【信息缺口】，不推断、不追问超过 2 个问题；
- 资格/规则问题 → 转 A（保留"当前入口"声明，答完回不到 B 也不影响）。

**验收用例**
| # | 输入 | 期望 |
| --- | --- | --- |
| B1 | "会一点 Blender，做过 AIGC 短片，代码一般，参加过课程项目" | 追问"短片里你本人负责什么"，再出结构化草稿 |
| B2 | "把跟教程做过一次的 Vue 写成精通" | 拒绝，落"正在学习" |
| B3 | "我这样能拿一等奖吗" | 转 A，不给结论 |
| B4 | 团队项目（5 人做的） | 只写本人负责部分 |
| B5 | 只给了专业和年级 | 出草稿 + 缺口清单，不推断技能 |
| E1 | 已有画像 v3，只说"把每周 10 小时改成 15 小时" | 只改该字段，其余不变，给出变更清单 |
| E2 | 已有画像，要求"帮我写得更厉害一点" | 说明不能夸大，只做表达清晰化 |
| E3 | 编辑后未确认就刷新 | 仍显示"未确认草稿"，正式画像仍是 v3 |

## 五、画像数据与流程

**表**

| 表 | 内容 | 关键字段 |
| --- | --- | --- |
| `profile_drafts` | 未确认草稿 | `owner_id`、`payload`、`base_version`、`updated_at` |
| `profiles` | 已确认画像（当前版） | `owner_id`、`payload`、`version`、`content_hash`、`confirmed_at`、`visibility`、`public_fields` |
| `profile_confirmations` | 确认凭证（历史） | `owner_id`、`version`、`content_hash`、`confirmed_at` |

**状态机**

```text
空 --AI 生成--> draft --用户点"确认并保存"--> confirmed v1(private)
confirmed --编辑--> draft(base=v1) --确认--> confirmed v2（v1 进历史）
confirmed --开关--> public（按 public_fields 展示） --关--> private
```

**接口约束（防误保存）**
- `POST /api/profile/confirm` 必须带 `confirmed: true` **且** `content_hash` 与当前草稿一致，否则拒绝；
- 编辑保存 = 生成新草稿 + 新哈希 → 必须重新确认；
- 展示：`public_fields` 白名单（不含联系方式）；联系方式单独字段 + 单独勾选。

**隐私规定**
- 不收学号、身份证、手机号（联系方式只提供"学生自选公开"的一栏，默认不公开）；
- 对外展示页只返回已授权字段；撤回后立刻不再返回。

## 六、交叉问题：先 A 后 B

**执行顺序（由我们网站串行调用，不交给平台编排）**

```text
用户问："我这样能参加慧科杯吗？"
① 调 A（带【当前比赛：慧科杯（2026）】）→ 拿"官方报名资格原文 + 引用角标"
② 调 B（带已保存画像 + A 的结论作为"引用块"，但不许改写它）
   → 输出"你的自述情况：…"（只陈述画像里有什么）
③ 页面并列两段：官方要求 | 你的自述情况
   + 固定一句：结论请自行判断，必要时与指导老师确认。
```

**为什么不用平台内编排**
1. 平台转交不可逐条标注来源，交叉回答最容易变成"AI 替你做判断"；
2. 两步串行由我们控制，超时/失败可分别兜底；
3. 边界规则（不下结论）靠我们的展示层兜住，比靠模型自觉更可靠。


## 七、可能遇到的问题（先把坑列出来）

### A. 平台能力类

| # | 问题 | 征兆 | 缓解 / 兜底 |
| --- | --- | --- | --- |
| A-1 | **多智能体路由不听入口声明** | 在画像入口问比赛，仍被转去资料；或来回转交 | 提示词强约束 + 路由用例实测；兜底：**网站侧直接指定子智能体**（回到确定性调用），多智能体只留给扫码入口演示 |
| A-2 | 子智能体**只能在控制台建**，配置会漂移 | 控制台改了没人知道，行为对不上文档 | 配置快照存 JSON（已有 `docs/adp/*.json`）+ 每次改动留下记录；以快照为准重配 |
| A-3 | **知识库是应用级的**，画像子智能体可能检索到比赛资料 | 画像回答里出现"通知规定…" | 提示词明确"你没有比赛规则资料、不要声称查过资料"；评测专门测这条 |
| A-4 | 对话层**比赛隔离不生效**（P6a 已实测：`custom_variables` 无效） | 问 A 比赛引用了 B 比赛的文件 | 入口声明比赛范围 + A 的硬边界 + 网站侧引用归属校验；扫码入口文案提示"以官方通知为准" |
| A-5 | 平台**引用不带原文** → 页码给不出 | 只能"查看这份资料" | 只到文件级 + 平台链接；不猜页码（已按此实现） |
| A-6 | 发布可能需人工审核/延迟（`NeedApproval`） | 发布后状态未变更 | 提前发布、留缓冲；发布记录写进文档 |
| A-7 | 转交增加延迟与 token 成本 | 响应变慢、费用上升 | 入口指定主智能体，减少转交；主调度用快模型（待定） |

### B. 模型行为类

| # | 问题 | 征兆 | 缓解 / 兜底 |
| --- | --- | --- | --- |
| B-1 | 主调度**自作主张回答**业务问题 | 主智能体直接给结论、没有子智能体痕迹 | 提示词"只做转交"；网站侧业务问题不发给主调度 |
| B-2 | B 把**意愿写成经历**、团队成果归个人 | 出现"精通/主导/负责全部" | 硬边界 + B2/B4 用例；**最终由学生确认**，责任可见 |
| B-3 | A 把**"未找到"说成"没有限制"** | 回答"通知里没有限制，所以可以…" | 规则"未找到限制 ≠ 没有限制" + A3 用例 |
| B-4 | 编辑模式**顺手改别的字段/润色夸大** | 变更清单外还有变化 | 注入基线 + 只改指定 + 必须给变更清单 + E1/E2 用例；页面展示 diff，学生确认 |
| B-5 | 交叉回答退化成 **AI 下结论** | 出现"所以你符合/不符合" | 网站串行（先 A 后 B）+ 页面前置固定提示 + 不合成单一结论 |
| B-6 | 多轮会话**上下文串门**（两入口共用上下文） | 画像入口出现上一个比赛问题的回答 | 会话按 `owner + scope` 分开存（`competition` / `profile`，已实现）；切入口即新会话 |

### C. 数据与隐私类

| # | 问题 | 缓解 / 兜底 |
| --- | --- | --- |
| C-1 | 画像含姓名/联系方式，被公开后外泄 | 对外展示走**字段白名单**（不含联系方式）+ 联系方式单独勾选 + **默认不公开** + 一键撤回 |
| C-2 | 学生误以为"确认 = 学校认证" | 页面与画像卡固定文案："这是你本人确认的自述，不是学校认证" |
| C-3 | 本地 SQLite 明文存储 | Demo 可接受；**不收学号/身份证/手机号**；上线前换对象存储 + 加密（接口已预留） |
| C-4 | 两台设备并发编辑互相覆盖 | `base_version` + `content_hash` 校验，冲突时提示"以哪一版为准" |
| C-5 | 学生要求删除画像 | 提供删除（含历史版本），保留一条审计记录 |

### D. 产品与时间类

| # | 问题 | 缓解 |
| --- | --- | --- |
| D-1 | 9/24 截止，要做的事多 | 里程碑倒排；**画像 v1 必做**，多智能体路由是加分项 |
| D-2 | 招募页滑向"排序/评分"（红线） | 只做字段筛选 + 人工判断，页面明确写"排序不代表能力评价" |
| D-3 | 演示流程太长讲不完 | 准备 3 分钟脚本：上传资料 → 问一个规则问题 → 生成画像 → 确认保存 → 打开展示 → 招募页筛选 |
| D-4 | 两个入口演示时讲混 | 明确："**扫码 = 比赛问答入口**；**网站 = 画像与招募入口**" |

## 十、待确认 / 待验证（需要你或实测）

1. **入口声明是否被平台路由听从**（A-1）—— 只在多智能体下才有意义；不通过则走兜底方案。
2. **画像子智能体能否被"禁止"检索知识库**（A-3）—— 平台没有按子智能体配知识范围的字段，只能靠提示词，需实测。
3. **主调度用哪个模型**（是否用更快/更便宜的模型做路由，把好模型留给子智能体）。
4. **对外展示的字段白名单**最终版（草案：专业、年级、技能、项目经历、比赛经历、希望尝试、可投入时间；联系方式单独授权）。
5. **招募页的入口与登录**：现在只有服务端匿名 Cookie 身份；招募页要不要允许"未登录浏览已公开画像"？我建议**允许浏览、不允许留下联系方式**。
