# 初赛范围与演示脚本（2026-09-20）

> 交付物：10 分钟内演示视频 + PPT + 在线访问链接/二维码 + 项目开发说明文档。
> 原则：**初赛只保证"演得出来"**；架构性增强（检索硬过滤、证据页码、编排器、完整资格核对体系）
> 归入"最终成品清单"，见第四节。

## 一、演示流程（按一个学生的真实过程走，主故事 8 幕 + 1 段能力展示）

### 主故事：从看比赛到找到队友

| 幕 | 屏幕 | 用户动作 | 系统表现 | 状态 |
| --- | --- | --- | --- | --- |
| 1 | 登录 | 选 **学生 / 老师** + 填名字 | 进来就是"登录" | 🟡 弹窗已有，**改文案 + 首屏触发** |
| 2 | 比赛库 | 浏览 3 场比赛（名称/截止/赛道/简介） | 一眼看出这是"管比赛的平台"，不是聊天机器人 | ✅ 已有 |
| 3 | 比赛详情 | 点进慧科杯 → **⭐ 关注比赛** → 问"一个人能参加吗" | **Agent A**：引原文回答 + 来源；关注后首页才出现「我的比赛」 | ✅ 问答已有 / 🟡 关注要做 |
| 3b | 比赛详情 | "我大二，数字媒体专业，一个人，能参加吗" | **资格逐项核对**：✅满足 / ❌不满足 / ⚪资料未规定 / ❓缺少信息 四态清单，每项带来源 | 🟡 **要做**（提示词 + 前端渲染成核对卡片） |
| 4 | 比赛详情 | 问"那我这种情况适合怎么准备" | A 发现缺个人信息 → **就地调用 B 的能力**：出现"补充一下你的情况"，生成一条画像草稿 →【加入我的画像】/【去画像页详细编辑】 | 🟡 **要做**（比赛页轻量调用 B） |
| 5 | 我的画像 | 点"查看完整画像" → 补一句"还做过 PPT 和演示视频" | **Agent B**：追问"这部分是你本人做的还是团队共同完成？" → 更新草稿 → 保存 → 打开"允许展示" | 🟡 **要做**（表单 + AI 整理 + 保存 + 开关） |
| 6 | 比赛详情 | 回慧科杯问"根据我的情况，我可以先做哪些部分" | A + 画像：官方要求 + 你已记录的经历并列，明确说"正在学习 Python 不能据此判断你能独立开发"，并提示可找队友 | 🟡 **要做**（把已保存画像注入 A 的请求；结果**只并列不下结论**） |
| 7 | 比赛详情 | "那我想找一个会开发的队友" | 不给推荐，提示："可以发布一条招募，你的画像可作为介绍展示 →" | 🟡 **要做**（关键词规则，非 AI） |
| 8 | 队伍招募 | 填比赛/标题/项目想法/希望队友参与/人数/联系方式 → 勾选"展示我的公开画像" → 发布 | 立刻出现在「招募广场」，并在「我发布的」里可见 | 🟡 **要做** |

### 第二段：系统的另一项能力（把资料变成比赛）

| 幕 | 屏幕 | 用户动作 | 状态 |
| --- | --- | --- | --- |
| 9 | 添加比赛资料 | 上传一份 PDF → AI 识别（比赛名/届次/发布方/赛道）→ 用户确认 | ✅ 已有 |
| 10 | 比赛库 → 新比赛 | 回比赛库看到新比赛卡片 → 点进去问"这个比赛几个人参加" | ✅ 已有（AI 依据刚上传的资料回答） |

> 上传放在主故事之后：它是"系统能力展示"，不是学生最核心的体验；这样视频节奏也更顺。


**登录假设**：全程只登录一次（浏览器记住），不做注册、不做密码、不做多账号切换。

## 二、页面与数据（初赛最小集）

| 页面 | 数据来源 | 本轮要做的 |
| --- | --- | --- |
| 登录弹窗 | `localStorage`（姓名 + 学生/老师） | 文案改成"登录"，首屏未登录时自动弹出 |
| 首页 / 比赛库 | `competitions` + **新表 `follows`** | 加「**我的比赛**」区块（关注的比赛，最多 3-4 张） |

## 二·补：闭环设计（"我的招募" + "我的比赛"，都不塞进画像页）

### 结论：区分三件不同的事

| 概念 | 生命周期 | 放哪 |
| --- | --- | --- |
| **我的画像** | 稳定（半年都可能不变） | 我的画像页（B 的主场） |
| **我的招募** | 临时（一场比赛一次，会结束） | 招募页的 `我的招募` 区域 |
| **我关注的比赛** | 中等（一场比赛结束后可取消） | 首页"我的比赛" + 右上角用户菜单 |

**不做"我加入的队伍"**：系统不追踪站外沟通结果，做出来是**假闭环**。
**也不把"我的招募"塞进画像页**：画像会被撑成"个人中心"，最后什么都往里堆。

### 招募页结构（两个区域，不是一个列表）

```text
队伍招募
├─ 招募广场（别人发布的）
│    卡片：比赛 · 标题 · 缺几个什么方向的人 · 是否公开画像 · 发布时间
│    └─ 详情：项目想法 / 希望队友参与什么 / 对方公开画像 / 联系方式
│              + 固定提示："请自行联系，平台不代做匹配与评价。"
└─ 我的招募（我发布的）
     ✅ 发布成功（发布后直接落在这里）
     卡片：比赛 · 标题 · 缺几人 · 状态（招募中 / 已结束）· 发布时间
     操作：[查看] [编辑] [结束招募]
     └─ 同一条同时出现在招募广场（发布 → 保存 → 对外展示，一眼看懂）
```

`recruitments` 表补一个状态字段：`status open / closed`（只有这两个状态，不要更多）。

### 用户菜单（轻量，不做个人中心）

右上角 `头像 / 用户名` 点开：

```text
我的画像
我的招募
我关注的比赛
我上传的比赛资料
退出登录
```

### 我关注的比赛（新增，比"我的队伍"更该补）

```text
比赛卡片 / 比赛详情 ──[⭐ 关注]──► follows(owner_id, competition_id)
                                        │
首页 ──►「我的比赛」区块（最多 3-4 张卡片，按关注时间倒序）
                                        │
用户菜单 ──► 我关注的比赛（全部）
```

**理由**：学生看完比赛、问了问题、做了画像、发了招募，**下次回来一定要能快速回到这场比赛**。

**初赛只做**：关注 / 取消关注、首页"我的比赛"区块、用户菜单入口。
**不做（下一步）**：截止提醒、倒计时、进度时间线 —— 这些需要先把"报名截止时间"结构化（属 `01-比赛信息智能解析` 的能力），现在做会不准。

### 视频里怎么演（避免"发布后就断了"）

```text
① 填招募 → 点【发布】→ 自动跳到「我的招募」→ 顶部 ✅ 发布成功（状态：招募中）
② 切到「招募广场」→ 同一条已在公开列表里
③ 回首页 → 「我的比赛」里慧科杯在第一位（刚关注过）
```

这样"发布 → 保存 → 对外展示 → 下次能找回"四件事一次演完。

### 页面总结构（冻结）

```text
登录
 ↓
首页 / 比赛库（含「我的比赛」区块）
 ├─ 比赛详情 ── 比赛智能体 A ＋ ⭐关注 ＋ "这场比赛招募（N 条）→"
 ├─ 我的竞赛画像 ── 画像智能体 B（唯一一份画像）
 ├─ 队伍招募 ── 招募广场 / 我的招募 / 详情 / 发布·编辑
 ├─ 添加比赛资料
 └─ 用户菜单 ── 我的画像 / 我的招募 / 我关注的比赛 / 我上传的资料 / 退出
```

### 身份：只做"展示标注"，**不做权限差异**（定稿）

- **登录只选一次**：姓名 +（可选）学生/老师，用途是**在资料、画像、招募上显示来源**：
  `来源：用户上传 · 张三（老师，自行选择）`；
- **不做角色权限**：不隐藏"发布招募"、不做老师后台。
  理由很实在：身份是自选的，谁都能选成学生 —— "老师不能发布"只是**假权限**，反而经不起评委追问。
  与既有口径一致：`uploader_role` 仅用于展示，**不参与任何判断**。
- 招募帖同理：显示"发布者：张三（学生，自行选择）"，不做限制。

### "这场比赛招募（N 条）"由谁算？

**普通数据库查询，不是 Agent A：**

```text
competition_id → 查 recruitments（status='open'）→ 列出该比赛在招募的帖子
```

### 职责分工（这句话要放进 PPT）

| 谁 | 负责 |
| --- | --- |
| **比赛智能体 A** | 比赛资料理解、规则问答、**资格逐项核对**、有限比赛分析 |
| **画像智能体 B** | 学生经历澄清、画像整理、画像修改 |
| **普通产品功能（非 AI）** | 关注比赛、招募发布/浏览/结束、资料上传、登录身份、统计计数 |

> 讲法：**"我们没有为了 AI 而把所有功能都做成 AI。只有需要理解和推理的环节用智能体，
> 确定性操作仍由普通系统完成。"** —— 这比"我们有很多 Agent"更站得住。

### 关注比赛：**必须用户主动点**（定稿）

视频里在第一次进入慧科杯时顺手点一下：`☆ 关注比赛 → ★ 已关注`，之后回首页才出现「我的比赛」。

**不允许**因为"问过这个比赛 / 填过画像 / 发布过这个比赛的招募"就自动加入「我的比赛」——
否则"关注"这个概念会变得不清楚。

### 明确不做（写进 PPT 的"下一步"）

- 申请加入 / 接受 / 拒绝 / 成员状态 / 队伍管理；
- 站内聊天、消息通知、申请提醒；
- AI 匹配度、队友推荐、能力评分；
- 截止提醒与倒计时（依赖结构化比赛信息）；
- "我加入的队伍"（等真有申请机制再说，且届时放**招募页**，不放画像页）。

### 已定稿
1. **身份**：只做展示标注（资料/画像/招募上显示来源），**不做权限差异**。
2. **招募帖人数**：保留 `need_count`（默认 1）。
3. **关注**：必须用户主动点，不自动加入。


recruitments(
  id TEXT PRIMARY KEY,
  owner_id TEXT,                      -- 发布者
  competition_id TEXT,                -- 针对哪场比赛（比赛页要用它筛"N 条招募"）
  title TEXT,                         -- 例如"寻找一名开发方向队友"
  idea TEXT,                          -- 项目想法
  want_role TEXT,                     -- 希望队友参与的方向（如"网页开发/后端接口"）
  need_count INTEGER DEFAULT 1,       -- 需要几人
  contact TEXT,                       -- 联系方式（学生自选公开）
  show_profile INTEGER DEFAULT 0,     -- 是否随招募展示我的公开画像
  status TEXT DEFAULT 'open',         -- open / closed
  created_at TEXT)
```

> 初赛**不做**：草稿/确认凭证/版本历史/并发校验（`draft + confirmed + hash` 那套工程化设计后移）。

## 三、本轮的"规则提示"（不靠 AI，靠代码，稳）

| 触发 | 提示 |
| --- | --- |
| 提问含 `队友 / 组队 / 匹配 / 找人 / 一起做` | "想找队友？先完善画像（或直接去招募页发布）→" |
| 画像保存成功后，回到比赛空间 | "画像已保存，可以发布招募了 →" |
| 招募页未填画像 | "先完善画像，招募会更有说服力 →" |

**画像"主入口"的理解**：**画像页 = 主入口**（完整表单 + 保存 + 展示开关）；
比赛空间里只放一句"去完善画像 →"的入口，**不重复做第二套表单**。

## 五、资格核对（优先做，这是和"PDF 问答"拉开差距的一屏）

**不是一句 Prompt，而是一个固定契约：四态 + 每项带来源。**

```text
用户：我大二，数字媒体专业，一个人，能参加这个比赛吗？

比赛助手：
✅ 满足     专业条件：官方明确"专业不限"            [来源：通知 第 1 页]
✅ 满足     队伍人数：官方要求 1-5 人，你 1 人符合    [来源：通知 第 2 页]
⚪ 资料未规定 年级条件：当前资料未找到年级限制         [来源：—]
❓ 缺少信息  学校身份：资料要求"本校在校生"，需你确认  [来源：通知 第 2 页]
❓ 缺少信息  指导老师：当前资料未提到，暂无法确认       [来源：—]

因此：目前不能完整确认报名资格，但"专业"与"队伍人数"两项已有依据支持。
```

**提示词规则（加进 A）**

```text
# 资格核对（用户问"我能不能参加/我符不符合条件"时启用）
1. 先从资料里逐条列出这场比赛的官方条件（每条带引用）。
2. 用户已提供的信息 → 逐项对照，只能用这四种状态：
   ✅ 满足 ／ ❌ 不满足 ／ ⚪ 资料未规定（当前资料未找到该条件）／ ❓ 缺少信息（需要用户补充）
3. 不允许出现"整体上你能/不能参加"的结论句；只给"哪几项有依据、哪几项无法确认"。
4. 资料之间冲突时：有明确废止/修改关系 → 说明替代关系；没有 → 保留冲突并列。
5. 不预测获奖、不评价能力、不推荐队友。
```

**前端渲染**：把四态各自用颜色/图标渲染成**核对清单卡片**（不是一段长文），每行右侧显示来源角标。
用户答"缺少信息"里的问题时，可以就地补一句，再点"重新核对"。

> 这一屏是初赛视频里最值钱的一屏：它证明 AI 在**读资料 + 读规则 + 逐项核对**，而不是"检索一段文字"。
