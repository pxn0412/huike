# 支持更多上传格式：怎么改 / 多久 / 会出什么问题

结论先说：**能改，而且不用推倒重来**。当前"只能 PDF"是四层叠出来的，其中入口那层 1 小时就能开，
真正花时间的是**"页"这个坐标**要泛化；另外机器上**已经装好了 docx/pptx 解析库**，OCR 脚本也跟 PDF 无关。

## 一、为什么现在只能 PDF（四层）

| 层 | 位置 | 现在怎么写的 |
| --- | --- | --- |
| 入口 | `index.html` `accept="application/pdf,.pdf"`；`store.py:229` 硬校验 `.pdf` 后缀 + `%PDF-` 魔数；`app.js:104` 只查 20 MB | 三道闸都在 PDF 上 |
| 解析 | `parsing.extract()` 用 `pypdf`，返回 **`pages = [第1页文本, 第2页文本, …]`** | 整条链路的数据模型就是"页数组" |
| 切片 | `chunking.build_blocks(pages)` → 块带 `page / page_end`，块首写"第 N 页"，跨页续写写"（接上页）" | **"页"是公共坐标** |
| 引用/预览 | `app.js:56` 写死 `· PDF 第 ${page} 页`；`viewer.html/js` 用 pdf.js `?file=…&page=N` 跳页；浏览器验收断言 `PDF 第`、`#total` | 点了就能跳到那一页 |

## 二、好消息：这三块已经现成

1. **`kb.py:23 read_pages()` 本来就支持非 PDF**：`.md` 按 `## 第 N 页` 读回，**纯文本按一页处理**。
   → 说明切片/知识库/检索链路对文本文件是通的，有先例可照抄。
2. **`ocr.ps1` 的输入是"目录里的 PNG"，跟 PDF 无关**（Windows 自带 OCR）。
   → **图片文件可以直接复用**：图片 → 缩放/转 PNG → 丢给 `ocr.ps1`。而且"一张图 = 一页"**语义天然成立**。
3. **依赖已经在机器上**：`python-docx 1.2.0`、`python-pptx 1.0.2`、`pillow 12.2`、`numpy`、`onnxruntime`、`bs4`、`markdownify`；
   但 `requirements.txt` **只写了 `pypdf==6.16.1`**（交付风险，见第四节第 7 条）。

## 三、怎么改（按格式分档）

**动手前先做一次抽象改造（2–3 小时，必须一次做掉）**

把"页"换成通用定位：`chunks.page` 保留给"真有页"的文件，另加 `locator`（形如 `第 3 页` / `第 2 节` / `第 1 张`）。
凡是写死页码的四处一起改：`chunking` 块首标注、`demo.ask` 提示词与来源格式、`app.js` 引用卡片、
`viewer` 跳转（非 PDF 时降级为"下载/新窗口打开 + 展示抽取到的文本片段"）。
> 好处：不显示页码**不违反**冻结稿 —— 原文就写着"页码仅在能核实时展示"。

| 档 | 支持 | 解析怎么做 | 增量工时 |
| --- | --- | --- | --- |
| **A1 纯文本** | `.txt` `.md` | 直接读；`.md` 复用 `chunking.read_markdown_pages()` | **2–3 h** |
| **A2 Word** | `.docx` | `python-docx`：`paragraphs` + **`tables`**（表格要单独遍历，否则漏内容） | **2–3 h** |
| **B 图片** | `.png` `.jpg` `.jpeg` | **复用 `ocr.ps1`**；一张图 = 一页 | **1.5–2.5 h** |
| C 其他 | `.pptx`（库已装）/ `.xlsx`（要装 openpyxl）/ 网页链接 | 每格式单独适配 | **每个 +2–3 h** |
| D 兜底（不推荐） | 任何格式 | 只托管原文件、能下载，**不进检索**，界面明说 | 1–2 h |

**推荐组合**：抽象改造 + 图片 + txt/md + docx ≈ **8–10 小时**（含测试、文案、文档）。
**赶时间的最优单点**：**只做图片（B）**，约 **4–5 小时**（含抽象改造的一半）—— 页语义天然成立、演示效果最直观。

## 四、会出现什么问题（按严重度）

1. **页码语义崩塌（最核心）**：docx/txt 没有页 → 引用卡片写不出"PDF 第 3 页"。
   必须改成"第 N 节 / 第 N 块"；**A 的回答里"来源：第 N 页"也会跟着变**，提示词不同步它就会编页码。
2. **"点引用直达原文页"要降级**：非 PDF 没有 pdf.js 的对应实现，只能给"下载 / 新窗口打开"或展示文本片段。
   ⚠️ 这是演示里最有说服力的动作之一（评委爱看），**做之前要想好视频里怎么切**。
3. **解析质量参差**：docx 的表格/文本框/图片里的字抽不到（`doc.paragraphs` 不含 `doc.tables`）；
   **老的 `.doc`（二进制）一律不支持**，要明确提示"请另存为 docx 或 PDF"，否则用户会以为是系统坏了。
4. **保护阈值失效**：现在的 20 MB / 200 页是运行保护；docx/txt 没页 → 必须改成**字数或块数上限**
   （否则一个 20 MB 的 txt 能塞几百万字，切片和检索都会垮）。
5. **混合内容**：docx 里贴的图片不会走 OCR（除非再做"抽图片 → OCR"，那是另一个工作量）。
6. **知识库侧联动**：块首标注、`render_markdown` 的"第 N 页"要一起改，否则知识库文本与网页显示不一致。
7. **交付依赖**：`requirements.txt` 必须补（`python-docx` 等）；否则换台电脑/交给评委就"跑不起来"。
   `.github-submit/` 快照也要重打。
8. **测试面扩大**：`check-demo.cjs` 里 `PDF 第`、`#total` 页数断言要改；`test_store.pdf_bytes()` 之外
   要加 docx/txt/图片夹具（docx 夹具可以直接用 `python-docx` 现造，不需要二进制样本）。
9. **上传页文案全要改**：「点击选择，或拖入 PDF」「最多 20 MB · 200 页」「正在读取 PDF 并保留页码…」
   「保留原始 PDF」—— 以及 `store.upload()` 的报错文案。

## 五、我的建议

1. **先做抽象改造 + 图片（B）**：最快见效、语义最正、演示收益最大（4–5 h）；
2. 有余量再加 **txt/md/docx**（+3.5–5 h）；
3. `pptx/xlsx/网页` **初赛不做**；
4. **方案 D（只托管不检索）不要做** —— 会在"每条结论都能核对原文"这个卖点上留洞，
   真要做必须在界面明写"这份资料暂不支持检索"。
